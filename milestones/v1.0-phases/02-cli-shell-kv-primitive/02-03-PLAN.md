From redis-py 7.x:
- `client.set(name, value, ex=None, keepttl=False) -> bool | None`
  - `ex=<int>` sets TTL in seconds (Redis `SET ... EX <int>`)
  - `keepttl=True` preserves existing TTL on update (Redis `SET ... KEEPTTL`)
  - `ex` and `keepttl` are mutually exclusive in redis-py — passing both raises DataError
  - For NEW keys with `keepttl=True`, Redis SET ignores KEEPTTL (no existing TTL to preserve) — safe but a no-op
- `client.get(name) -> str | None` (None if key missing; empty string "" if key set to "")
- `client.delete(*names) -> int` — number of keys actually deleted
- `client.scan_iter(match=None, count=None) -> Iterator[str]` — cursor-based prefix scan; safe for large keyspaces; returns decoded strings due to `decode_responses=True`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-supplied key string → KEY_PREFIX concatenation | A key containing `:` would let the user write into `state:lock:*` or `state:claim:*` namespaces if validation were absent |
| user-supplied value string → Redis SET | Redis values are byte-safe; the risk is resource exhaustion (oversize) and accidental binary pollution |
| kv.py → redis_client | Single-chokepoint invariant per D-18; any direct redis.Redis() here breaks the Phase 1 error-translation contract |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-03-01 (T-2-02 cross-namespace key collision) | Tampering | `validate_key` | mitigate | KEY_REGEX rejects `:` explicitly (D-09); validation runs BEFORE prefix concatenation; tested in `test_validate_key_rejects_colon` and `test_kv_list_scope_excludes_lock_and_claim` |
| T-2-03-02 (T-2-01 command injection via state set) | Tampering | `kv_set` argv handling | mitigate (defense in depth) | Plan 04 passes user value through typer (no shell); kv_set itself only calls `client.set(...)` which transmits via the redis-py wire protocol (no shell interpretation). No mitigation needed in kv.py beyond the API contract. |
| T-2-03-03 (T-2-03 value-size DoS) | Denial of service | `kv_set` value argument | mitigate | `MAX_VALUE_BYTES = 1_048_576` cap; ValidationError raised before any Redis call; tested in `test_kv_set_rejects_oversized_value` |
| T-2-03-04 (D-18 single chokepoint regression) | Tampering | direct `redis.Redis()` construction | mitigate | grep-gate in acceptance_criteria (`grep -cE "redis.Redis\("` returns 0); structural test in Plan 05 enforces the invariant tree-wide |
| T-2-03-05 (Information disclosure via error messages) | Information disclosure | ValidationError messages | mitigate | Locked messages do NOT include the rejected value (only the regex spec or the byte cap). `KvNotFound` carries only the user-typed key (already known to the user); message construction lives in Plan 04's verb layer where it explicitly formats `"key '<key>' not set"` |
| T-2-03-06 (SCAN cursor leaking concurrent writes) | Tampering | `kv_list` cursor consistency | accept | Redis SCAN is best-effort under concurrent writes (may double-return a key, may miss a key inserted after the scan started). Acceptable for Phase 2 since `state list` is a developer/debugging surface, not an authoritative ledger. Documented in module docstring. |
