Land the LOCK-03 `--hold` wrapper: `em-proj state lock --hold <name> -- <cmd...>` auto-acquires the lock, spawns `<cmd>` as a subprocess, runs a daemon refresher thread that re-EXPIREs the lock every ttl/3 seconds, and releases the lock on subprocess exit (normal exit, signal received by the python parent, or atexit). Plus the multi-process harness tests that prove ROADMAP success criterion #5 (two children racing --hold serialize correctly).

Purpose: --hold is "the pattern that makes locks actually used correctly" (PROJECT.md M1 active req). Bare `lock`/`unlock` is the building block; `--hold` is the ergonomic surface that every real consumer (memory-file edits, build steps, gsd-sdk hooks) will use. Without --hold, every caller hand-rolls the acquire-run-release dance and inevitably gets one of the three steps wrong.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User-supplied `cmd: list[str]` → subprocess.Popen | argv vector; could be a malicious binary path |
| Signal delivery → cleanup handlers | OS-level interrupt; could race with the cleanup or fire during cleanup |
| Refresher thread → Redis | Long-lived connection from a daemon thread; could leak on parent crash; could lose Redis mid-run |
| Wrapped subprocess inherits parent's TTY → could re-read holder data | Out of scope — that's an em-proj-internal trust boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-05-01 | Signal-handler race (T-3-XX-04) | lock_hold_run cleanup | mitigate | Cleanup helper is guarded by `_cleanup_done: threading.Event`; double-invocation is a no-op. Lock release goes through Lua compare-and-delete (Plan 03-03 LUA_COMPARE_AND_DELETE) which is idempotent — if our lock was already deleted by --warn override or TTL expiry, the script returns 0 and the cleanup catches HeldByAnother silently. The cleanup ordering is documented: subprocess terminated → stop_event set → refresher joined → lock_release. |
| T-3-05-02 | Command injection | cmd list[str] → subprocess.Popen | accept (no shell) | `subprocess.Popen(cmd, ...)` with `cmd: list[str]` and NO `shell=True` does not invoke a shell. Each argv element is passed as-is to execve. The user-supplied vector is exactly what runs — no metacharacter expansion. This is the same posture as multiproc_race (Phase 1 design). |
| T-3-05-03 | TOCTOU between acquire and refresher start | gap window | mitigate | The window is microseconds: lock_acquire writes the holder JSON, then the thread is `start()`ed. If the python parent crashes in that window, the TTL backstop (60s default) covers — the lock auto-releases within a minute. The refresher's first EXPIRE call is at `interval` (~20s for default TTL), so the first ~20s relies on the initial SET NX EX. |
| T-3-05-04 | Refresher loses Redis mid-run + parent crash leaves orphan thread | RefresherThread | mitigate (Blocker #3 pin) | **Recovery posture documented + enforced:** If Redis goes down during `--hold`, the refresher catches `redis.ConnectionError`/`redis.TimeoutError` (the ONLY narrow except in lock.py), logs a one-line stderr warning per failed EXPIRE, and keeps looping. The lock expires at its TTL backstop (default 60s) if Redis stays down. **The wrapped subprocess is NOT aborted on refresher failure** — best-effort survival over noisy abort. Unexpected exceptions (anything else) cause the refresher thread to log + re-raise so the thread dies with a visible signal rather than swallowing bugs silently. The thread is also `daemon=True` — process exit kills it without graceful shutdown if the parent itself crashes.
